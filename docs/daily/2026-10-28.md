## Hasan (Backend / AI)

**Definition of done:** `ruff check app tests` clean, `pytest` green (14 old + your new
tests), `scripts\verify-auth.ps1` still exits 0, and every new endpoint callable from
`http://localhost:8000/docs`.

### 1. Complete data model — one Alembic migration
- All core tables from the plan §1: `incidents, incident_reports, assessments, poll_votes,
  verification_events, response_tasks, task_updates, assignments, alerts, user_alert_prefs,
  audit_logs, assist_conversations, assist_messages, simulation_runs, routing_edges,
  map_locations, external_feeds_cache` + the `users` tables you already have.
- **The four axes on `incidents`** (this is the anti-cheat core):
  `assessment_status (UNASSESSED|DEFINITELY_FALSE|MAYBE_TRUE)`, `visibility
  (HIDDEN|PUBLIC_UNVERIFIED)`, `verification (UNVERIFIED|VERIFIED|REJECTED)`,
  `response_phase (NONE|COORDINATING|ACTIVE|RESOLVED)`, `lifecycle (OPEN|CLOSED)`,
  plus `category` (8 enums, AD-15), `sensitivity (PUBLIC|RESTRICTED)`, NCR `region`.
- Keep AD-3: **`sim_*` tables have zero FKs to live tables.** No FK to `users` from
  simulation output either.
- How: `cd code\api; .venv\Scripts\alembic.exe revision -m "core schema"`, review the
  generated file, then `docker compose up -d` (entrypoint runs `alembic upgrade head`).
  Verify: `docker exec astra-db-1 psql -U postgres -d astra -c "\dt"` lists every table.

### 2. Seed script — 5 demo roles + permission matrix
- `scripts/seed.py` (or alembic data migration): one account per role with predictable
  demo logins (e.g. `admin@astra.dev`, `dephead@astra.dev`, `team@astra.dev`,
  `officer@astra.dev`, `citizen@astra.dev` — same password you can remember) + NCR seed
  incidents across all 8 categories.
- Permissions come from `app/core/permissions.py` (single source; seed must not invent
  its own copy — import `permissions_for`).
- Verify: login as each in `/docs` → `/auth/me` returns the right role + permission list.

### 3. Audit middleware — every mutating request writes `audit_logs`
- FastAPI middleware (or dependency on mutating routes): `actor_id, role, action,
  method, path, before/after or resource_id, request_id, ip, timestamp`. Append-only —
  no UPDATE/DELETE endpoints, ever.
- At minimum covered: register, login (success **and** failure), refresh, and every
  future write route (incidents, tasks, verification, alerts).
- Verify: `docker exec astra-db-1 psql -U postgres -d astra -c "select action, path from audit_logs order by created_at desc limit 10"`
  after a login; add a pytest asserting a login inserts a row.

### 4. Object-level scoping helper
- `require_permission("x")` exists (403 gate). Add the **scope** layer: a helper that
  answers "may this user act on THIS object?" — dept head sees only own department's
  incidents/tasks. Signature idea: `assert_in_scope(user, obj)`.
- Write the contract test now: dept head of Fire trying to open a Police task → 403/404.

### 5. Contract tests for everything you add
- New test file(s) next to `tests/test_auth_contract.py`; same pattern (httpx
  `ASGITransport`, isolated `astra_test` DB — conftest already handles it).
- Keep AD-12: no new code lands with a red ruff or pytest.

**EOD check:** all 5 roles login → `/auth/me` correct; every POST writes an audit row;
cross-department access is refused by the backend (curl shows 403/404, not 200).

## Lubna (Frontend / UI-UX)

**Definition of done:** `npm run build` clean, and you can click through login → the right
dashboard for each of the 5 demo roles without touching the API by hand.

### 1. Screens: login, signup, demo role picker
- `/login` (email + password), `/signup` (name, email, password), and a
  **demo role picker** (5 one-click logins — pure demo convenience, clearly labelled
  "demo login", never in production paths).
- Real wiring, not mocks, for auth: `POST /api/v1/auth/{login,register}` against
  `http://localhost:8000` (CORS already allows `localhost:3000`, AD-5). Put the calls in
  `src/api/auth.ts`, logic in a `useAuth` hook, state in `stores/auth.ts`.
- Token handling per AD-2: **access token lives in the Zustand store (memory, lost on
  refresh is acceptable for v1)**, refresh token in `localStorage`; auto-refresh once on
  401 then retry.

### 2. Route guards driven by permissions (visual)
- Next middleware / layout guards: unauthenticated → `/login`; authenticated → redirect
  by `user.permissions` (e.g. no `incident.verify` → verification queue hides).
- Remember: this is **visual only** — the backend enforces (Hasan). Never rely on it.

### 3. Dashboard shell per role + placeholder cards
- Same layout shell, sidebar items filtered by permissions (5 roles look distinctly
  different — this is what the demo shows on Day 5's Module 1 milestone).
- Placeholder cards where APIs don't exist yet, using the mock layer from Day 1.

### 4. Shared component library (build these 7 first)
- `StatusBadge` (the 4 status axes colours: UNVERIFIED amber, VERIFIED green,
  DEFINITELY_FALSE grey, CLOSED slate), `RoleGate`, `DataTable`, `Card`, `Modal`,
  `EmptyState`, `Toast`. Document one-line usage in the file header — Hasan reads them
  too.

### 5. Type sync
- After login lands, regenerate `contracts/types.ts` from `openapi.json`
  (`http://localhost:8000/openapi.json`) and import those types in api/store layers —
  no hand-written duplicate interfaces.

**EOD check:** `npm run dev` → demo-pick each of the 5 roles → correct sidebar + cards;
kill the API (`docker compose stop api`) → your UI shows an **error state, not a blank
screen or console red** (zero visible errors in the demo is a hard rule).
